## Changes Made

### #1 — Production Dockerfile for Teleplex Payload CMS
**Files:** `sites/teleplex/payload/Dockerfile` (new)
**Approach:** Started with Option A (multi-stage, Next.js standalone). The standalone build worked but `output: 'standalone'` produced broken symlinks in the pnpm monorepo — native modules (`next`, `sharp`, `libsql`) couldn't resolve in the runner stage. Switched to **Option B (fat stack)** — single-stage image that copies the full monorepo, installs deps, builds in-place, and runs `pnpm start`.
**Final Dockerfile:**
- `node:22-alpine` base with corepack pnpm 10.10.0
- Copies full monorepo, `pnpm install --frozen-lockfile`
- Deletes all `.env` files and `data.db` artifacts before build (to prevent build-time DB creation)
- Builds with inline dummy env vars (`DATABASE_URL=file:/tmp/build-data.db`)
- Sets `ENV NODE_ENV=production` and `ENV DATABASE_URL=file:./data/data.db` for runtime
- `VOLUME /app/sites/teleplex/payload/data` for SQLite persistence
- `HEALTHCHECK` on `/api/health` every 30s
- `ENTRYPOINT` + `CMD` pattern

### #6 — Fix SQLite Schema Initialization Bug
**Problem:** First container boot threw `SQLITE_ERROR: no such table: users` when hitting `/admin/login`.
**Root cause:** Payload 3.x's SQLite adapter (`@payloadcms/db-sqlite`) with `push: true` has a race condition in production (`next start`) mode. The DB file exists but schema tables aren't created before the first query runs.
**Fix:** Added `push: true` to `sqliteAdapter` in `sites/default/payload/src/shared/payloadBase.ts`, then pivoted to **Payload migrations** as the production-standard solution:
- Generated initial migration locally via `pnpm payload migrate:create`
- Committed migration file to `src/migrations/`
- Entrypoint runs `pnpm payload migrate` before `pnpm start`
- Migrations initialize all tables before any API request

## Decisions & Rationale
- **Option B (fat stack) over Option A (standalone):** Standalone output had broken pnpm symlinks (`next`, `sharp`, `libsql` missing in runner). Fat stack is larger (~3.5GB) but reliable.
- **Migrations over `push: true`:** `push: true` has a known race condition in Payload 3.x production. Migrations are the intended production path and guarantee schema exists before queries run.
- **Inline env vars during build:** `ENV` directives in Dockerfile can be overridden by copied `.env` files. Inline vars on the `RUN` command are highest precedence.
- **Keep `push: true` in `payloadBase.ts`:** User requested leaving it alone for now (useful for local dev).
